# Нагрузочная проверка Cloudflare

**Статус 16.10.2026:** генератор и автоматизация остановлены по просьбе пользователя. FinanceAcademy перенесена на https://finacademy.kz (VPS в Астане, PostgreSQL). При переносе проведены только функциональные проверки; нагрузочные тесты не запускались. Исторические записи ниже не являются подтверждением производительности VPS и не разрешают возобновление нагрузки.

Сценарий выполняет 300 независимых авторизованных HTTP-сессий с одного компьютера. Это проверка API и сохранности данных, а не запуск 300 браузеров. Результат относится к указанному стенду, версии и сетевому маршруту; при переносе на VPS нагрузка проверяется повторно.

## Профиль

- 300 вымышленных аккаунтов `load001`–`load300` в отдельной группе. Учебные студенты и попытки RU/KZ не используются.
- Техническая копия русского банка: 200 вопросов, случайные 25 каждому студенту. Окно 75 минут оставляет время для старта и завершения после полного часа нагрузки. Настройки учебных RU/KZ остаются 60 минут.
- Одновременный вход, массовый запуск и получение управляющей сессии.
- Полные 3600 секунд после подтверждения сервером 300 активных попыток. Каждые 15–19 секунд с разбросом — новое сохранение; каждый пятый цикл — компактное продление сессии без изменений.
- Чтение и сравнение серверных ответов и неизменности снимка после старта и далее примерно каждые 12 минут.
- Отправка дубликата события прокторинга с проверкой единственного нарушения.
- Раз в минуту администратор подтверждает все 300 активных попыток. Итоговая проверка выполняется до массового завершения.
- Завершение 300 попыток, повторное завершение для проверки идемпотентности; административная сверка всех 7500 ответов, оценок и журналов.

## Повторение

```powershell
npm run load:prepare-hour
npm run load:hour
# В другом терминале:
npm run load:status
```

Подготовка использует приватные `.local/load-fixture.json`, `.local/msfo/deployed.json` и `.local/seed-state.json`. Доступы не входят в отчёт и публичные assets. Каждому аккаунту разрешено до 20 технических попыток; завершённые результаты сохраняются. Нельзя повторять подготовку во время текущего прогона: она обновляет настройки технического теста.

Отчёт текущего запуска сохраняется примерно каждые 20 секунд в `output/load/<время>.json`. После завершения создаются одноимённый Markdown и `latest.json`/`latest.md`. `load:status` читает самый новый отчёт, включая незавершённый. Наличие параметра 3600 само по себе не подтверждает прохождение часа: проверяется фактически истекшее время и контрольные серверные выборки.

## Измерения

Клиентские p50/p95/p99 включают получение всего тела ответа. `Server-Timing` отдельно показывает время обработки Worker, включая его обращения к D1; это не время чистого SQL. Метка `X-Worker-Colo` отражает поле `cf.colo` запроса и не доказывает место исполнения Worker после placement. Версия приложения учитывается для каждого ответа.

Сетевые ошибки, 429 и 5xx повторяются максимум три раза. Все исходные неуспешные запросы и повторные отправки остаются в счётчиках. Ошибки прикладной проверки, конфликт владельца вкладки или потеря ответа не скрываются повтором. Функциональная проверка и целевые задержки оцениваются отдельно: успешные результаты не означают автоматически p95 < 2 секунд.

Цель производительности: клиентский p95 входа, запуска, сохранения и завершения менее 2000 мс, доля ошибок менее 1%. Для компактных фоновых запросов задержки также публикуются. Функциональная цель: 300 активных попыток весь час, 300 подтверждённых результатов, 7500 сохранённых ответов, корректные оценки и отсутствие дублирования результатов.

## Оптимизации

Обычный запуск создаёт снимок и приватный ключ из одной материализованной выборки SQL. Сохранение и компактный heartbeat проверяют актуальную сессию, блокировку, владельца попытки, управляющую вкладку, срок и версию в одной атомарной операции. Сохранение проверяет каждый идентификатор вопроса и варианта по снимку. Для истёкших попыток, конфликтов и повторных пакетов остаётся полный обработчик с прежними правилами. Кеш авторизации не используется.

Фронтенд не загружает тексты вопросов при каждом idle heartbeat. В D1 добавлен индекс истечения сессий. Worker закреплён в регионе рядом с основной D1; статические файлы обслуживаются Cloudflare Assets. Счётчик активных попыток использует отдельный покрывающий индекс и не пересчитывает всю историю каждые 10 секунд. Полная статистика обновляется раз в минуту.

## Автономный облачный генератор

`scripts/cloud-load/worker.mjs` создаёт 300 отдельных авторизованных HTTP-сессий. По 10 сессий используют один планировщик Durable Object: 30 планировщиков, циклы с разбросом 19–20 секунд, независимые cookie/версии/ответы каждого студента. Запросы идут в публичный API приложения; прямого доступа к D1 у генератора нет. Отдельный Monitor проверяет число активных попыток раз в минуту. Coordinator сохраняет обезличенные метрики в KV `LOAD_REPORTS`, доступные через Cloudflare API, даже если локальный интернет нестабилен.

Приватные данные для запуска готовит `node scripts/cloud-load/bootstrap.mjs` (или `--smoke` для одной сессии/60 секунд). Они сохраняются только в `.local/cloud-bootstrap-secrets.json`, затем загружаются как секреты отдельного Worker. `trigger.mjs` инициирует Coordinator, `pull.mjs` скачивает отчёт через Wrangler. Время начала и окончания задаёт сам облачный сервер; сравнивать его абсолютные часы с часами локального компьютера для вычисления длительности нельзя.

Сейчас генератор **остановлен**: `LOAD_PAUSED=1`, cron отключён. Не включать его, пока не восстановлена квота D1. Для нового разрешённого прогона: подготовить новый run ID через `bootstrap.mjs`, загрузить секреты, установить `LOAD_PAUSED=0`, опубликовать конфигурацию, выполнить `trigger.mjs`, затем получать отчёты через `pull.mjs`. После испытания вернуть `LOAD_PAUSED=1`, отключить cron и опубликовать конфигурацию. Само изменение флага не восстанавливает суточную квоту и не доказывает прохождение нагрузки.
